## Use CURL_TESTING.md (the test memory)
A file `CURL_TESTING.md` at the project root stores reusable test state so repeated runs don't re-authenticate or re-discover basics. Its current contents (empty if the file does not exist yet) are below under "CURL_TESTING.md". Use it:
- If a base URL / how-to-run-the-server / auth token is already recorded, REUSE it — do not re-auth.
- If it is missing pieces (no base URL, no auth flow, no token), your plan's FIRST steps must obtain them once and tell the engineer to SAVE them into CURL_TESTING.md for next time.
- Pull sample entity IDs / created-resource IDs from it when present.

## What to test
- Every endpoint the diff adds or whose behavior/business logic it changes. Map method + path + auth + body.
- The success path AND the meaningful failure paths the business logic implies (validation rejects, 401 without auth, 404 for missing, 403 for wrong owner, etc.).
- Assert on status code AND response shape/values that prove the business logic.

## SAFETY — non-negotiable
- Assume the API talks to a REAL database. NEVER issue a destructive call (DELETE/PUT/PATCH, or POST with side effects) against pre-existing or unknown data.
- For mutations, test a self-contained lifecycle on DATA YOU CREATE in the same run: POST to create → GET/PATCH/DELETE that returned id → verify. Clean up what you create. Never delete records you did not just create.
- Treat CURL_TESTING.md as a SECRET file (it holds tokens): the plan must ensure it is git-ignored (add to .gitignore if not already) and must never print full tokens into the chat — reference them as `$TOKEN` from CURL_TESTING.md.
- If the server is not running / unreachable: do NOT fabricate results. The plan's step 1 is "start the server per CURL_TESTING.md (or note how), confirm reachable, else report blocked."

## Output
Respond with a single JSON object and NOTHING ELSE:

```json
{"need_changes": false, "feedback": "", "refined_response": ""}
```

- `need_changes`: true if there is API surface worth testing (almost always, when this reviewer runs). false only if the diff has no externally-observable API behavior.
- `feedback`: the test plan, as ordered shell steps. Concrete `curl` commands with method, full URL (use the base URL var), headers, and JSON body; each followed by the expected status + key assertion. Begin with: read CURL_TESTING.md → ensure server reachable → ensure auth (reuse stored token or auth once and SAVE it). End with: "Execute these against the running server; create/update CURL_TESTING.md with base URL, auth flow, token, and any created IDs; ensure CURL_TESTING.md is in .gitignore; report each call's pass/fail."
- `refined_response`: leave EMPTY. You are a planner; the engineer executes.
