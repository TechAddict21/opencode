# CLI Launch & Branding

How the `nous` CLI is launched and where the "nous" name surfaces to the user. The product is a rebrand of `opencode`; the npm package name is still `opencode` and many internal paths/env vars keep the `opencode`/`OPENCODE_` prefix, but everything user-facing must read `nous`.

## Launch chain
`nous` (global) → `~/.noussh/bin/nous` → `exec run.sh "$@"` → one of two modes:
- **Production**: `exec`s the compiled single-file binary `packages/opencode/dist/opencode-<platform>-<arch>/bin/nous`.
- **Development**: `exec bun run --conditions=browser src/index.ts` (used when no native binary is found).

`run.sh` auto-detects: prefer production, fall back to dev. `--dev`/`--prod` force a mode; `--build` builds first; `--install` (re)writes the `~/.noussh/bin/nous` shim.

## The terminal-tab gotcha (most important)
The VS Code terminal tab shows the **foreground process's executable name** — NOT yargs `scriptName`, NOT the OSC title the TUI emits. So the *only* thing that makes the tab read "nous" is the executable itself being named `nous`:
- Production → process is the compiled binary → tab shows its filename (`nous`).
- Dev → process is `bun` → tab shows "bun". On macOS this is unavoidable in dev mode: `comm` is fixed at exec from the binary path; `process.title` changes `ps -o command` but not `comm`, so VS Code still reads "bun".

The binary filename is set by THREE places that must stay in lockstep — change one and the others silently break:
1. `script/build.ts` `outfile` — names the built binary.
2. `run.sh` `find_native_binary` candidate path — must match `outfile`, else production is never found and `run.sh` silently falls back to dev mode (tab shows "bun").
3. `bin/nous` launcher (`binary` const + `findDistBinary`) — the npm-install resolution path.

> Historical bug: renaming `build.ts` `outfile` from `bin/opencode` → `bin/nous` without updating `run.sh`'s candidate made `run.sh` miss the binary and drop to dev mode, so the tab flipped from "opencode" to "bun".

Note: the dist *directory* is still `opencode-<platform>-<arch>` (derived from `pkg.name`); only the binary file inside is `nous`.

## Key Files
- `run.sh` (repo root) — the real launcher. `find_native_binary` (candidate `dist/opencode-${platform}-${arch}/bin/nous`), `run_production`/`run_development`, and `install_global` (writes the `~/.noussh/bin/nous` shim). Editing the binary name? Update line ~65 here.
- `packages/opencode/script/build.ts` — `outfile: dist/${name}/bin/nous` (~209) and the post-build smoke-test path (~228). Source of the binary filename.
- `packages/opencode/bin/nous` — npm-distributed Node launcher; spawns the compiled binary. Holds `binary`/`findDistBinary` (must be `nous`) and emits an OSC title sequence + `process.title`.
- `packages/opencode/src/index.ts` — yargs entry. `.scriptName("nous")` (help/usage text), `show()` gating on `text.startsWith("nous ")`, and `process.title = "nous"`.
- `packages/opencode/src/cli/cmd/tui/app.tsx` — `createEffect` (~347) calls `renderer.setTerminalTitle("Nous" | \`nous | ${title}\`)`, gated by `terminal_title_enabled` KV and `Flag.OPENCODE_DISABLE_TERMINAL_TITLE`. Sets the OSC title but does NOT override VS Code's process-name-based tab.

## Notes
- `scriptName` only affects yargs `--help`/usage output; it never touches the OS process name or the terminal tab.
- `~/.noussh/bin/nous` is generated by `run.sh --install`; it just `exec`s `run.sh`, so all launch logic lives in `run.sh`.
- A 100MB+ file at `dist/.../bin/nous` is the compiled Bun binary; its mtime tells you whether the last build succeeded.
